## Team access

On the game, open **Table settings → AI**, enter the shared team password, then choose **Unlock AI**. Unlock before starting an AI-enabled **Solo quest** or **Gather party** adventure (one human is enough). Enable the AI storyteller during setup to customize the quest. The browser remembers access for up to a year and defaults to AI enabled after the first unlock. **Disable AI** saves an off preference without forgetting access; **Enable AI** restores it without another password. **Forget this device** revokes access and clears the cookie. Existing requests can finish, other browsers remain unchanged, and saved stories/cached audio stay available. Clearing browser data, expiration or a password rotation requires a fresh unlock. Site visitor permissions are separate: the password does not grant access to an invite-only Site.

The host supplies `AI_ACCESS_PASSWORD_HASH`, generated by this helper in an interactive terminal:

```sh
node scripts/team-password.mjs
```

The input is hidden. Copy its output into ignored `.dev.vars` locally, or save the value as a **Secret** named `AI_ACCESS_PASSWORD_HASH` in Site settings. Never paste the actual password or API key into Git. The verifier uses PBKDF2-SHA256 with a random salt and 100,000 iterations. Replacing it and restarting/redeploying invalidates old unlocks. Missing or malformed configuration fails closed for paid work.

The server enforces access on campaign start, dictation, narration and suggestions/audio, including direct HTTP requests. Session cookies are HttpOnly, SameSite=Strict and Secure on HTTPS; only hashed opaque tokens are persisted. Unlock attempts are limited to five per IP/minute and thirty across the site/minute. Session storage is bounded. The browser cannot change models, server opt-ins or spending limits.

## Teammate development using the owner's account

1. Pull the shared code and run the normal setup/tests without a key first.
2. Obtain the existing project API key from the owner through a private password manager or another secure channel. GitHub access and a game password do **not** reveal or copy the key.
3. Put `OPENAI_API_KEY=<the privately shared key>` in the root `.dev.vars` on your own computer. It is ignored by Git. Do not put it in frontend code, screenshots or prompts.
4. Generate a local password verifier with the helper above, add it to that same file, and add the small-experiment settings below. Build, apply outstanding migrations and run `npm start -- --port 5347`.
5. Unlock in **Table settings → AI**, then create an AI-enabled Solo quest or Gather party adventure. Restore `AI_MODE=fixture` and restart when paid testing is finished.

This uses the owner's API billing, not the teammate's payment method. Local D1 ledgers are **separate**: they do not share the hosted game's allowance or other developers' usage. Agree on each person's testing budget. A shared raw API key can call any model/endpoint its OpenAI project permissions allow, including code outside this game's safeguards. A separate key per teammate in the same funded OpenAI project is an optional later improvement for revocation and tracking; it need not mean each teammate pays. This feature does not provide a general API proxy or add the Decisions API.

## Play and persistence

### Story-first creator

New solo and party creation now follows **Your idea → Narrator → Story → Character → Play**. Join-party keeps its short hero/invite flow. The first screen accepts an optional premise and narrator description. Personality, Speaking style and Appearance each offer short preset labels and up to three selections, with custom values checked for category fit. Conversation can generate and refine three distinct narrator profiles. Each displays the same validated character recipe in both Paint and Pixel.

The selected narrator creates a short editable synopsis, timeline, world/planet and key locations. Conversation receives the current edited draft and recent messages. Players then choose among three story-linked heroes or create their own through conversation, personality/background traits, direct edits and supported class/palette choices. Length, companions and rules come last. Reviewed story content is installed directly at start; no second planner can overwrite it. World/location facts, narrator identity and hero background persist with the campaign and replay. The selected narrator replaces Pip in the board prompt, avatar, live narration, guidance and speech delivery.

`POST /api/quest/create` uses the existing bounded Luna Responses adapter, strict JSON schemas and independent validation. Each paid request requires team access and the quest's AI opt-in, with durable reservations and replay-safe deduplication. AI-off creation runs built-in drafts on the client without database or provider access. Fallback drafts are labeled. A failed or cancelled request retains the current choices and conversation input.

Every narrator **Play** press requests a new short audition and a new Realtime clip. Auditions use Marin with the selected persona and speaking-style instructions; previous audition text is supplied to encourage variety. Clips are bounded to 12 seconds and kept in the browser for playback. The durable ledger retains a delivery/charge receipt, so audition media does not fill the reusable story-audio cache. Repeating an old request never charges again; its transient clip may no longer be available, and a new Play press deliberately requests a new sample. The existing paid-audio gate, transcript verification, cancellation, deadlines and shared spending limits apply. Unavailable voice shows a text sample and a clear status. No browser key, new provider or novel bitmap generator is introduced.

Creation schemas constrain text lengths, short labels and option counts before generation, followed by independent parsing. The Responses adapter distinguishes intermediate commentary from the schema-bearing final answer, following the [official phase guidance](https://developers.openai.com/api/docs/guides/reasoning#phase-parameter). Current narrator candidates and the original brief accompany conversational refinements, while story and character conversations receive the current edited draft.

The following paragraphs record the prior guided-setup implementation and remain useful for its dictation, gameplay and persistence details.

All development/tests default to fixtures. A key alone changes nothing. Settings → Table → **AI adventures** selects the default for new quests; setup's **AI storyteller** switch overrides it for that quest. Neither player control enables paid server access. Setup guides the player through hero, story and review; joining a party uses hero and invite steps. Rules, narrator direction, character traits and world seed stay under optional fine-tuning. Creative prompts are limited to 400 characters each.

Offline solo stays local. An AI-enabled **Solo quest** creates a saved server room with the selected companions and starts it directly. A failed start leaves a recoverable party camp instead of creating a duplicate. **Gather party** uses the same server AI boundaries but waits at camp for invitations/readiness. Server rooms require D1 even when paid AI falls back to fixtures. Short, Standard and Long select 1, 3 and 5 playable chapters respectively; these are chapter counts rather than guaranteed minutes. Longer adventures reuse the existing validated encounter families.

With AI enabled, players can describe a quest and setting or expand optional story ideas. Dictation records visibly for at most 60 seconds. After **Stop & transcribe**, the recording is sent to the server; the completed transcript receives conservative filler/stutter/whitespace cleanup. Players review and edit before adding it to the quest, and unapplied transcripts block setup and header navigation until used or discarded. Browser Back preserves the review, and full-page departure uses an unsaved-work warning. Existing typed text is retained. Cleanup does not ask a second model to rewrite the player's story; it aims to preserve names, exclusions and intent. The player can type if microphone access, server AI or allowance is unavailable.

During play, open **Pip** from the board. **How do I play?**, **What next?** and **Ask Pip** provide read-only guidance grounded in the current objective and legal actions. Under **Guide the story**, the host can persist a new creative direction, request brisk narration or request an ending at the current chapter's gateway. Ending early still requires completing the encounter, collecting its shard and reaching the gateway. Models never perform actions or bypass rules. Bots remain scripted.

Pip has paired Paint/Pixel avatars with talking and blinking animation and reduced-motion support. **Tell this moment** saves a caption from committed events; AI quests also save one telling at chapter boundaries and the ending. **Listen** can reuse generated server audio when separately enabled, with device speech as fallback. Stop and captions remain available; playback stops after 45 seconds or when leaving/changing the moment. The host generates new narration/audio, and everyone can reuse cached audio.

The planner supplies the premise and companion names, personalities and palette choices. Character recipes keep validated classes and stable IDs; human names/classes remain fixed. Existing paired SVG libraries render each recipe in Paint/Pixel and 2D/2.5D, and common trees, path tiles and scenery are reused. No raster-image model or unconstrained asset generation is connected. Heroes retain identity across chapters; character leveling remains future work.

Accepted campaigns, identities, chapter memories, story direction and narration persist in the game/replay. Later narration receives the completed chapter summaries, saved traits, current objective and committed events, allowing it to build toward the engine-owned ending. Polling, replay and presentation changes never generate. Resume does not regenerate the saved campaign, art or tellings. Old saves remain intact; new campaign metadata requires a new adventure. A seed varies local starting material but does not make model prose deterministic. Narration remains bounded flavor, not a semantic guarantee against hallucination. Saved prompts are visible to room members: do not enter secrets.

## Spending safeguards

Defaults: $0.10/campaign (the persisted session), $0.25/UTC day, $1/UTC month, two global outstanding calls. Server configuration can raise ceilings up to the owner-authorized $0.50/campaign, $2/day and $25/month. Invalid/zero caps disable live requests. Defaults remain small for new local checkouts; a higher hosted budget does not propagate to developers. D1 compare-and-swap reserves allowance **before** outbound traffic across concurrent workers/users. Reconnect does not reset spending. Missing persistence fails closed.

Text requests are bounded to 16,000 UTF-8 bytes, 1,600 output tokens for planning or 500 for narration/intent/guidance. No tools, automatic paid retries or streaming. Player requests and chapter/ending transitions can generate; polling does not. Reservations use byte-based input bounds plus 2,048 framing tokens, cache-write rates and a 2× margin. This is conservative accounting, **not exact provider billing**. Failed calls retain reservations; reported usage is saved without automatic refunds. At maximum input size Luna planning reserves ~$0.006112 and narration ~$0.005012; Terra planning reserves ~$0.06112 (too large for the suggested $0.05 experiment). Typical inputs are smaller. Provider price changes, taxes and external charges are separate; recheck rates before enabling.

Dictation accepts only verified mono 16 kHz 16-bit PCM WAV, at most 60 seconds / 1,920,044 bytes. It reserves $0.020000 before an outbound transcription request (a conservative margin over the documented [GPT Transcribe duration price](https://developers.openai.com/api/docs/models/gpt-transcribe); see [file transcription](https://developers.openai.com/api/docs/guides/speech-to-text)), uses a recording-specific pre-quest scope under the durable global day/month caps, and caches by recording hash. The server bounds the response and enforces a deadline; failures retain their reservation and there are no paid retries. Duplicate successful recordings reuse their transcript. Raw audio is not stored in the ledger; the validated transcript and cleaned text are cached, so avoid dictating secrets. Microphone permission and capture happen in the browser only after selecting Dictate quest; no audio is sent while recording.

Audio accepts at most 600 characters and a 4,096-byte request, allows 1,800 output tokens, and reserves 79,373 microdollars before even connecting. The calculation is 2 * ((4,096 + 2,048 framing tokens) * $0.60/M + 1,800 * $20/M). Charging every output token at the audio rate conservatively includes text and reasoning output; cached input is charged at full input rate, with a 2x margin. No input audio, images, transcription or tool fees can be incurred by this path. Each attempt allows one response, 15 seconds wall time including connection, 30 seconds decoded audio (240,000 mu-law bytes), 1 MB wire events, 350 KB per event and 2,000 events. Text also times out after 15 seconds.

Audio is buffered until completed, then the streamed transcript (when supplied), completed audio transcript and final message transcript must agree with the approved caption. Normalization permits whitespace and one balanced enclosing double-quote pair (straight or curly), as observed in live output. Interior punctuation, case, numbers, words and word order remain exact; missing/added words or changed stories are rejected. Deviations, missing transcripts and truncation fall back to device speech. This checks reported transcripts, not audible verbatim fidelity. The request uses explicit no-context reading instructions with the caption quoted as data. The clip is stored compactly as mu-law and served as mono PCM WAV. Stop, leaving the dialog, changing the moment and HTTP request abort cancel pending work; an independent deadline closes it even if the runtime cannot propagate client disconnect. No partial audio plays. Voice volume/speed apply to paid and device playback; zero volume makes no audio request. Refused, malformed, stale or failed output falls back without changing rules. Intent is deduplicated per room/player/event even if the text changes. Narration is once per event, maximum 100 saved captions per campaign.

The durable ledger stores receipts, validated results/cache and usage, never credentials. Dictation results include transcript text; room creative prompts persist with the campaign. It stops at 2,000 receipts or 600,000 UTF-8 serialized bytes. Reservations account for pending results before connecting: 321,000 bytes for speech, 32,000 for text or 16,000 for dictation, plus receipt overhead. Oversized results cannot be committed. This deliberately small shared ledger may fit only one maximum-length clip; storage exhaustion falls back without paid regeneration. Successful clips are keyed by room, approved text, model, voice and adapter version, shared by all players and repeated identical captions, and remain readable after paid generation is disabled. Failed attempts are also deduplicated. A crash may leave a pending receipt occupying a concurrency slot. Do not reset/delete it to retry uncertain paid work: reconcile provider usage first. Manual ledger maintenance is deliberately outside gameplay; this is a small local prototype, not an indefinite billing database.

OpenAI documents both alerts and enforced hard limits; alerts alone do not stop calls, and hard limits may slightly overshoot while usage propagates. This task changes neither. [Spend limits documentation](https://developers.openai.com/api/docs/guides/spend-limits). App reservations cover only this app's requests.
